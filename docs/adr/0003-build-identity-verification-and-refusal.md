# 用构建身份核验取代版本字符串比较

ADR-0001:11 已经指出「相同版本号不足以证明相同构建」。本 ADR 把这句话落成一条可执行的检查：启用替换的前提不是版本号相等，而是**运行中安装的构建身份**等于来源清单里记录的构建身份。构建身份是对一份固定包清单内所有文件（递归，排除符号链接与嵌套 `node_modules`）按安装根相对路径排序后，逐行累加 `sha256(path + "\0" + sha256(content))` 得到的摘要；清单与算法随交付包发布（`packages/dsh-client-ui-settings/lib/baseline-identity.js`），摘要值记录在 `provenance.json` 的 `baseline.buildIdentity`。

清单是**策划的**，不是依赖闭包：16 个与设置页、远程调用、凭据和插件加载直接相关的包（DSH 自身安装根、`dsh-base`、`dsh-web-app`、设置组件族、`dsh-api-*`、`dsh-credentials*`、`cordis*`）。实测该清单 308 个文件、7,649,159 字节，枚举加哈希约 24 毫秒，可以承担每次启动的核验；把 CLI 的完整依赖闭包纳入会变成 547 个包、57,555 个文件、约 700 兆字节、约 1.2 秒，代价与收益不相称，因此否决。当前记录的摘要为 `bced54ff05f16443449162f00be33c2a0aea802d7f5046648262c0185942e321`。

核验是**失败关闭**的，没有豁免通道：预检（`tools/verify-artifacts.mjs` / `tools/overlay.mjs preflight`）不通过时，终端入口拒绝安装或切换，且 `profile` 目录逐字节不变——不存在「先装上再补救」的中间状态；运行时 `apply()` 的第一条语句就是 `assertBaselineIdentity()`，不认环境变量、不认版本范围、也不认任何「兼容性豁免」，因为豁免一旦存在就绕过了自有检查。发现「哪份安装」的顺序也遵循同一条原则：运行时以**本进程的启动脚本**为锚点（`process.argv[1]` 指向的 `<install>/lib/bin.js`），`DSH_INSTALL` 只作为终端与测试调用方的显式覆盖排在后面——一个能被环境变量改写的门禁等于没有门禁，何况环境变量还能把门禁引向另一份获准的安装、同时掩盖真正在跑的代码。

运行时拒绝的后果是**如实**的：实例继续运行，但设置 provider 不被提供（页面拿不到可用的设置界面），对该命名空间的写入被拒绝（`settings/rejected`），既不会假报成功，也不会悄悄降级回上游。恢复只能在终端做——`diagnose` 找出不符之处，`rollback` 退回原组合，`record` 在确认新基线后重新记录；替换不宣称能自动恢复原设置界面。

替换与回退的边界同样要精确。`enable` 会把 profile 自己 patch 里已有的 `- id: ui-settings` 覆盖行的 `name` 守卫一并改写成自有组件名并保留其 `config`：不然那条已保存的配置会因为守卫不匹配而整条被跳过，用户会看到设置「自己变回去了」。`rollback` 只做反向的两件事——把守卫改写回上游包名、把**当前** `dsh.profile.bundles` 里的自有组合换回它顶掉的上游 roster——不把状态文件里记下的旧列表整份写回，这样替换期间新增的其它层不会被一并删掉；状态文件只用于知道原 roster 是否存在，不用来复原整份选择。

身份核验覆盖的是**安装的构建**，不是 profile 里已装的打包产物：后者被改坏（例如 `lib/client.js`）不影响构建身份，由 `diagnose` 把它与记录里的 sha256 逐个比对并以文件名指出来。两者的恢复动作也不同——前者要换回获准的构建或重新记录，后者重装包或回退即可。

局限与 ADR-0001 一致：身份只覆盖那份 16 个包的清单，其余目录（含依赖的嵌套 `node_modules`）不在核验范围内；换基线必须重新记录并重跑证据；本仓不签名、不固定 tarball 哈希、不校验 pnpm 锁文件。
